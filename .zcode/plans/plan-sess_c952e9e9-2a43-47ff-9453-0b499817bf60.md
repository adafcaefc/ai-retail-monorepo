# Rebuild "Requirement vs inbound supply" from `synthetic.demand_store_sku_32w`

## Root cause
The chart is computed in the browser by `computeRequirement()` — `frontend/src/agents/retail/replenishment/data/selectors.js:364`. Requirement is `Σ ADS × day` (a straight line) and cover is `on_hand + open_po` with step jumps, because one ADS per SKU is all the workbook holds. The new table provides a real 32-week demand backbone (16 actual + 16 forecast weeks per store×SKU; 16,000 rows; joins 800/800 to `retail.dim_item` and 160/160 to `retail.dim_store`; chain totals run 1.60M→1.73M actual, 1.81M→1.91M forecast). It is even calibrated to this board: chain `Σ forecast_w1` = `Σ ads × dow_sum(7.45)` to 5 significant figures. Source files are already in the repo: `resources/demand_store_sku_32w_poc_v1.csv` (16,000 rows, identical column contract) + `_manifest.json`.

## Confirmed decisions
- **Weekly grain, 32 points**: labels `W-16…W-1 | W+1…W+16`, dashed Today divider in the middle ("current = middle of the data"), matching the mockup (`splitAt`).
- **Requirement = plain weekly demand units** (actuals for history, forecast for future). No ×1.03 lift — consistent with the repo's documented refusal of the mockup's unexplained factor.
- **Cover = modelled lagged supply**: `cover(w) = 0.5·demand(w) + 0.5·demand(w−1)` — the mockup's lag model *without* its fabricated every-4th-week 0.86 dips. No arrival dates exist in any table, so cover stays a documented model; the gap opens naturally because demand grows. *(Dips were not explicitly confirmed — flagged as vetoable in review.)*
- **A3 (Replenishment) only**; replacing Demand Forecasting's `FAKE_HISTORY_MULTIPLIERS` is a follow-up using the same payload pattern.
- **Seed from the committed CSV** so any environment can reproduce the table.
