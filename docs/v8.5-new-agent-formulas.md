# v8.5 new agent formulas — spec, not implemented

This catalogs the 10 formulas that are new in the v8.5 workbook (as opposed
to the 2 existing formulas — ADS per store, Max — that v8.5 revised; those
were synced into `resources/dbtemp/formula.json` / `retail.formula` as part
of the v8.2→v8.5 database migration). Each one below is tied to a "*_live"
sheet that didn't exist in v8.2 and has no path into the database yet. This
document is the spec for building that path — it isn't built here.

For context on the migration itself and what *did* ship, see the DB
migration plan this followed (drop/recreate of the 14 workbook-owned
`retail.*` tables, `sql/retail/006_add_dim_item_archetype_pattern.sql`, and
the ADS/Max sync).

## Why these are real feature work, not a data refresh

Every other v8.5 change (14 new `ENGINE_STORE` columns, 3 new `SKU_Master`
columns, 2 new `Replenishment Detail` columns) is a raw *input* the existing
engine formulas consume — re-extracting and re-seeding picked those up
automatically because Excel had already done the computation. These 10 are
different: they're new *outputs*, computed on brand-new sheets
(`A1 Accuracy live`, `A5 Markdown live`, `Live per-SKU (GMR)`,
`A8 Vendors live`, `A9 Summary live`, plus reconciliation sheets for
A2/A3/A4/A6/A7), and nothing in `retail.*` or the dashboard code reads them.
Building each one needs: a `SheetSpec` entry in
`scripts/extract_workbook_schema.py` for its source sheet, a schema change,
a seed-builder mapping, a `retail.formula` entry with a worked example, and
actual backend (`backend/src/llm/agents/retail/<agent>/dashboard.py`) +
frontend wiring for that agent's dashboard.

## The 10 formulas

### 1. Accuracy % — Agent 1 (Demand Forecasting)
- **Formula**: `100 − MAPE`, where `MAPE = volBase×26.6 + shapeErr×0.4 + storeVol + hzPen`
- **Source sheet**: `A1 Accuracy live` (120 rows) — section "Bagian A · Build-up MAPE"
  breaks MAPE into named components (`volBase`, `shapeErr`, `storeVol`, `hzPen`),
  each with a value, a weight, and a plain-language note.
- **Replaces**: the current `accuracy_pct` in `demand_forecasting/tools/demand_data.py`,
  which is an explicit "TYPED CONSTANT, NOT A BACKTEST" (92.4% stated
  identically for all 8 verticals — see that file's `warning` string). This
  formula is the first real per-vertical accuracy figure in the workbook.
- **To build**: `SheetSpec` for `A1 Accuracy live`; a table to hold the 4
  MAPE components per vertical; a `retail.formula` entry (grain: likely a
  new `vertical` grain — none of the existing three, `store_sku`/`chain_sku`/
  `store_roster`, fit "per vertical, not per SKU or store"); dashboard change
  to stop presenting `accuracy_pct` as a typed constant.

### 2. Avg markdown depth — Agent 5 (Pricing & Markdown)
- **Formula**: `Σ(depth_i × v_i) ÷ Σ(v_i) × 100` — value-weighted average
  markdown depth, rounded at the end (not per-SKU).
- **Source sheet**: `A5 Markdown live` (23 rows, 12 SKUs) — columns `SKU`,
  `Name`, `State`, `Position`, `Max`, `UnitsExp`, `Price`, `baseDepth`,
  `depthAdj`, `depth_i`, `atRiskU`, `v_i (Rp)`, `depth×v`. `MD lever (%)` is
  an editable input (row 6) feeding `depthAdj`.
- **To build**: `SheetSpec` for `A5 Markdown live`; per-SKU markdown table
  (grain: `store_sku` or a new item-level grain — check whether `Position`/
  `Max` here are chain-level like `ENGINE` or store-level like
  `ENGINE_STORE`); `retail.formula` entry; wire into the Pricing & Markdown
  dashboard/tools alongside the existing `markdown_recoverable`/
  `markdown_at_risk_value` columns from migration 004.

### 3. GMROI — Agent 6 (Assortment)
- **Formula**: `annual GM ÷ avg inv cost`
- **Source sheet**: `Live per-SKU (GMR)` (131 rows, 42 cols) — the richest
  new sheet, covering Agents 2–6 for one vertical (GMR, 100 SKUs) end to
  end: input columns (`Price`, `Margin`, `Growth`, `Cann`, `Fund`, ...)
  through every intermediate (`Position`, `ROP`, `Max`, `State`, `AtRisk`,
  `depth`, `sellThru`, `incrMargin`, ...) to `GMROI` itself in the last
  column. Row 5 carries the same lever block (`Horizon`/`hzCov`, `MD %`,
  `Promo %`) as `Constants`.
- **Also see**: `A6 Assortment live` (18 rows) — a smaller GMROI +
  contribution/cumulative-share table, same shape as `agent_kpi_reference`'s
  existing `retail.assortment_optimization` entries but per-SKU instead of
  per-vertical.
- **To build**: this sheet alone could seed a genuinely new
  `retail.fact_assortment_detail`-style table (grain: `store_sku` or
  chain-SKU, needs deciding); `retail.formula` entry for GMROI; Assortment
  dashboard change to show real per-SKU GMROI instead of only the five
  `agent_kpi_reference` aggregates noted as pasted-not-formula in
  `seed_retail_facts_from_json.py`'s `build_agent_kpi_reference` docstring.

### 4. Vendor score — Agent 8 (Vendor & Brand)
- **Formula**: `0.35·OTIF + 0.30·Fill + 0.20·LeadAdh + 0.15·(100 − defect×8)`
- **Source sheet**: `A8 Vendors live` (21 rows, 8 vendors) — `Vendor`,
  `#SKU`, `GMV (Rp/wk)`, `Margin (Rp)`, `Funding (Rp)`, `OTIF`, `Fill`,
  `LeadAdh`, `Defect`, `Score`, `Fund%`, `Margin%`.
- **To build**: `SheetSpec` for `A8 Vendors live`; add `score`, `gmv_weekly`,
  `fund_pct`, `margin_pct` to `retail.dim_vendor` or a new
  `retail.fact_vendor_scorecard`; `retail.formula` entry; Vendor & Brand
  dashboard change.

### 5. Route — Agent 3 (Replenishment)
- **Formula**: category-based classification — `fresh/salmon/parting →
  Direct`, `promo/seasonal → Flow-Through`, everything else → `Cross-Dock`.
- **Source**: the new `Route` column directly on `Replenishment Detail`
  (already captured raw in `resources/dbtemp/schema_with_data.json` as
  `replenishment_detail.route` — see the extraction fix in
  `scripts/extract_workbook_schema.py` that stops reading before the
  sheet's trailing "Route summary" block). Also surfaced in
  `A3 Replenishment live`.
- **To build**: add a `route` column to `retail.replenishment_proposal`
  (additive migration, same pattern as 006); map it in
  `seed_retail_facts_from_json.py`'s `build_replenishment`; `retail.formula`
  entry documenting the classification rule; Replenishment dashboard change
  to show/filter by route.

### 6. Fill rate — Agent 3 (Replenishment)
- **Formula**: `(total SKU − SKU reorder) ÷ total × 100`
- **Source sheet**: `A3 Replenishment live` (42 rows) — worked example over
  8 Fashion SKUs referencing `ENGINE` rows directly, plus a per-vertical
  reconciliation block.
- **To build**: `retail.formula` entry (grain: `vertical`, same open
  question as Accuracy %); no new raw data needed — `is_reorder` already
  exists on `retail.replenishment_proposal`, so this is mostly a
  `retail.formula` + dashboard aggregation change, not new ingestion.

### 7. Service level — Agent 9 (AI Summary)
- **Formula**: `100 − (stockout ÷ total SKU × 10%)`
- **Source sheet**: `A9 Summary live` (14 rows).
- **To build**: `retail.formula` entry; `is_stockout` already exists on
  `retail.fact_inventory_daily`, so again mostly formula + aggregation, not
  new ingestion.

### 8. Total value identified — Agent 9 (AI Summary)
- **Formula**: `Σ` of 6 components, each with a haircut applied to avoid
  double-counting (explicitly "anti dobel hitung" in the Formulas sheet).
- **Source sheet**: `A9 Summary live` — a `Komponen` / `Live (formula)` /
  `Engine` / `Cek` / `Sumber` reconciliation table. First 3 rows seen:
  "Overstock value × 0.40" (Σ MAX(0, Position−Max) × price × 40%, i.e.
  excess only, not full inventory value), "Markdown recovery" (from
  `A5 Markdown live`), "Promo incremental margin" (Σ `ENGINE_STORE` column Z,
  live).
- **To build**: needs #1–7 above substantially in place first, since this
  formula composes across nearly every other agent's live figures. Do this
  one last.

### 9. PT positions — Agent 7 (Workforce Optimizer)
- **Formula**: `residual gap ÷ 0.5 FTE per part-timer` (4-hour shift;
  `Constants!B10` "Part-time FTE" = `20h ÷ 40h` = 0.5).
- **Source sheet**: `A7 Workforce live` (33 rows) — per-vertical roll-up of
  Required/Scheduled/Gap/Surplus FTE (already live on the `Workforce` sheet
  itself, columns N/O/P) plus this new PT-positions figure.
- **Important dependency**: `Constants!B10` was a real bug in v8.2 (7.45,
  a copy-paste of the unrelated "DOW sum" constant; fixed to 0.5 in v8.5 —
  see the DB migration's Context section). It is **not referenced by any
  currently-implemented formula** — this is the one place v8.5 makes it
  load-bearing. Get the value from `retail.formula`'s Constants table (once
  extracted) or hardcode 0.5 with a comment citing this file; don't
  re-derive it from `Full-time h/wk` ÷ `Part-time h/wk` without also fixing
  it if the workbook's constant ever drifts again.
- **To build**: `retail.formula` entry; small addition to the Workforce
  Optimizer dashboard.

### 10. hzCov — Agents 2/3 (cross-cutting)
- **Formula**: `MAX(2, Horizon ÷ 2)` weeks, feeding `Max = ADS × (Lead +
  Safety + hzCov)`.
- **Status**: already implemented — this is the same `hzCov` synced into
  `f06-maximum-inventory` during the DB migration (`Constants!B24`, value 4,
  derived from `Constants!B23` "Horizon (weeks)" = 8). Listed here for
  completeness since the Formulas sheet lists it as new; no further work
  needed unless `A2 Inventory live` / `A3 Replenishment live`'s
  reconciliation views are also built out.

## Open design question before starting

Formulas #1, #6, and #7 (Accuracy %, Fill rate, Service level) are all
per-vertical, not per-SKU or per-store — none of `retail.formula`'s three
existing grains (`store_sku`, `chain_sku`, `store_roster` — see
`scripts/import_formulas_to_db.py`'s `GRAIN_FROM_SHEET`) fit. Decide whether
to add a `vertical` grain (`retail.agent_kpi_reference` already keys on
`vertical_id`, so there's a natural home) before writing any of these three
into `retail.formula` — guessing here would be exactly the kind of silent,
permanent mistake `import_formulas_to_db.py`'s docstring warns against.

## Suggested order

1. Route (#5) and Fill rate (#6) — smallest, mostly reuse existing columns.
2. Service level (#7) and PT positions (#9) — small, one new dashboard field each.
3. Decide the grain question above, then Accuracy % (#1) and Vendor score (#4).
4. GMROI (#3) and Avg markdown depth (#2) — need new per-SKU detail tables.
5. Total value identified (#8) — depends on the others being done first.
