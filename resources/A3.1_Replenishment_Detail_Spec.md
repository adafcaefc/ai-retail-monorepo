# Agent 3.1 · Replenishment Detail — Functional & Data Specification

**Source workbook:** `Copy of AI_360_Retail_Dataset_v8.2_General_20260806.xlsx`  
**Primary sheet:** `Replenishment Detail`  
**Related dashboard spec:** `A3_Replenishment_Dashboard_Spec.md`  
**Upstream sheets:** `ENGINE`, `SKU_Master`, `Trade Agreement`  
**Downstream process:** replenishment recommendation → requisition review → PR / PO creation → SoA approval → ERP execution

> **Important:** this specification describes the actual `Replenishment Detail` worksheet and the expected detail-screen behavior. The workbook sheet is not store-level. Its current grain is one row per SKU, with 800 rows covering eight verticals. Store-level inventory exists separately in `ENGINE_STORE` and must be added explicitly if the application detail page is expected to support Store filtering.

---

## 1. Purpose

The Replenishment Detail page provides the line-level evidence behind Agent 3 replenishment recommendations. It should let a planner:

- identify which SKUs require replenishment;
- validate On Hand, Open PO, inventory Position, ROP, and Max;
- review order quantity in sales and purchase UOM;
- see the designated vendor and active Trade Agreement price;
- compare the designated vendor against the best valid price;
- quantify line amount and potential procurement savings;
- select eligible lines for requisition, PR, or PO creation;
- preserve an auditable link between the recommendation, formula inputs, vendor decision, approval, and ERP output.

### Current workbook population

- **Data rows:** 800 (`Replenishment Detail!6:805`)
- **Verticals:** DGT, ELC, FSH, GMR, GRC, HNB, HNL, OMN
- **Current grain:** one row per Item/SKU
- **Current key:** `Item`
- **Purchase UOM values:** Box, Carton, Case, Crate, Pack, Pallet, Sack, Set

## 6. Core Formulae

### 6.1 Inventory reconstruction

```text
Qty on hand = MAX(0, Position - Open PO)
Position    = Qty on hand + Open PO
```

Current workbook example, row 6:

```text
Qty on hand = MAX(0, ENGINE!F6 - ENGINE!V6)
Open PO     = ENGINE!V6
```

### 6.2 Reorder trigger

```text
Reorder? = IF(Position < ROP, "YES", "—")
```

This is a strict less-than comparison. `Position = ROP` does not trigger reorder.

### 6.3 Recommended quantity

```text
Order qty (sales) = MAX(0, Max - Position)
```

The actual quantity is sourced from `ENGINE!O`, so Replenishment Detail must not silently introduce a different netting formula.

### 6.4 Sales-to-buy UOM conversion

```text
Order qty (buy) = CEILING(Order qty (sales) / Pack factor, 1)
Ordered sales units = Order qty (buy) × Pack factor
```

The ceiling operation can intentionally create a quantity above the unconstrained `Max - Position` requirement.

### 6.5 Purchase amount

```text
Amount = Order qty (buy) × Pack factor × Unit price (TA)
```

The current workbook price is treated as a price per sales unit. Therefore, Amount must multiply by Pack factor. Labeling Unit price as “per buy UOM” would be incorrect for the current formula.

### 6.6 Best-price vendor

```text
Best price = MIN(valid candidate Trade Agreement prices)
Best-price vendor = vendor associated with Best price
```

### 6.7 Potential saving

```text
Saving vs designated =
    Order qty (buy)
  × Pack factor
  × (Designated unit price - Best unit price)
```

A negative saving should not be shown as an opportunity. In production, apply:

```text
MAX(0, calculated saving)
```

## 7. KPI Summary Specification

| KPI | Formula | Unit | Interaction |
|---|---|---|---|
| Reorder SKUs | `COUNT(Reorder? = YES)` | SKU count | Click applies `Reorder? = YES` |
| Order qty (sales) | `SUM(Order qty sales)` | sales units | Respects all filters |
| Order qty (buy) | `SUM(Order qty buy)` | mixed buy UOM count | Must not be presented as a physically additive quantity across different UOMs without UOM segmentation |
| Purchase amount | `SUM(Amount)` | IDR | Opens top-value lines |
| Potential saving | `SUM(Saving vs designated)` | IDR | Applies positive-saving filter |
| Alternate-vendor opportunities | `COUNT(Best-price vendor <> Designated vendor AND Saving > 0)` | SKU count | Opens vendor comparison view |

> **Critical display rule:** summing `Order qty (buy)` across Carton, Case, Crate, Pack, Pallet, and other UOMs produces a mathematically valid count but a weak operational KPI. Prefer sales units, value, or a breakdown by Buy UOM.

## 8. Main Grid Behavior

### 8.1 Default view

- Default filter: `Reorder? = YES`
- Default sort:
  1. `Amount` descending
  2. `Saving vs designated` descending
  3. `Item` ascending
- Freeze: Item, Item name, Reorder?

## 10. Bulk Selection and Actions

### 10.1 Selection rules

A line is action-eligible only when:

- `Reorder? = YES`;
- Order qty sales and buy are greater than zero;
- Buy UOM and Pack factor are present;
- selected vendor has a valid Trade Agreement;
- price and currency are present;
- no unresolved data-quality exception exists.

### 10.2 Supported bulk actions

- Export visible lines to CSV
- Export selected lines to CSV
- Select designated vendor for all lines
- Apply best-price vendor where eligible
- Create requisition draft
- Create PR draft
- Create PO draft, grouped by vendor, legal entity, currency, delivery destination, and route
- Submit selected document set to SoA approval

### 10.3 Action safeguards

- Do not auto-switch vendor solely because it has the lowest price.
- Validate approval status, lead time, MOQ, capacity, agreement validity, and currency.
- Require a reason for manual quantity or vendor override.
- Recalculate Amount and Saving after every override.
- Prevent submission if the recommendation snapshot has changed since selection.

## 14. Data Quality and Validation Rules

### Required validations

- Item must exist in `SKU_Master` and `ENGINE`.
- ROP and Max must be non-negative.
- Max should be greater than or equal to ROP.
- Open PO and Qty on hand must be non-negative.
- Order qty sales and buy must be non-negative.
- Pack factor must be greater than zero when order qty sales is positive.
- Buy UOM must be present when order qty buy is positive.
- Unit price and Best price must use the same currency and price-unit basis.
- Designated and best-price vendor must be approved for the Item.
- Trade Agreement must be valid on the execution date.
- Amount must tie to ordered sales units × designated unit price.
- Saving must tie to ordered sales units × price difference.
- Reorder status must tie to Position < ROP.

## 17. Critical Findings

1. **The current sheet is SKU-level, not Store × Item.** It has 800 rows and no Store field. Any document claiming 16,000 store-item rows is describing a target design or `ENGINE_STORE`, not the actual `Replenishment Detail` worksheet.

2. **On Hand is reconstructed, not directly sourced.** `Qty on hand = MAX(0, Position - Open PO)`. This loses information if the upstream components ever produce a negative difference and may not match physical on-hand semantics.

3. **Trade Agreement matching is position-dependent.** The formulas use fixed three-row ranges per SKU, such as rows 6:8, 9:11, and 12:14. This assumes exactly three aligned Trade Agreement rows per SKU in the same order as `ENGINE`. Inserting, deleting, or re-sorting one sheet can silently break vendor-price matching. Production logic should join by Item, vendor eligibility, date, currency, UOM, quantity tier, and legal entity.

4. **Best price alone is insufficient.** Lowest unit price does not prove lowest landed cost or best operational choice. Lead time, MOQ, capacity, service level, freight, quality, and contractual constraints need independent eligibility checks.

5. **Price basis must be explicit.** The Amount formula multiplies `Order qty buy × Pack factor × Unit price`, which means Unit price is treated as price per sales unit. The UI and API must not label it as price per buy UOM.

6. **UOM rounding creates intentional over-ordering.** The rounded sales quantity may exceed `Max - Position`. Show both raw requirement and rounded ordered units, plus the uplift.

7. **The sheet is a recommendation snapshot, not an execution ledger.** It lacks run ID, timestamp, approval state, and ERP document status. Those fields are mandatory before using the page for real PR/PO execution.

8. **Open PO has no ETA or availability confidence.** Counting all Open PO in Position may understate the new requirement if inbound is delayed, partially confirmed, or outside the planning horizon.

9. **Mixed Buy UOM totals are not operationally meaningful.** Summing Crates, Cartons, Pallets, and Packs into one buy-quantity KPI should be avoided or segmented.

10. **Scenario consistency must be enforced.** If What-If changes demand, inbound, lead time, or safety stock, every detail-line quantity, amount, vendor comparison, KPI, and export must be recalculated from the same scenario version.
